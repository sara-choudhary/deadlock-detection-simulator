# Deadlock Detection Simulator

An interactive web application that detects deadlock in a system of processes and resources.
You describe what each process holds and what it is still waiting for; a Flask backend runs
the standard deadlock *detection* algorithm for resource types with multiple identical
instances, and the page shows which processes can finish, which cannot, a step-by-step trace,
and why the stuck processes are stuck.

Operating Systems mini project (deadlock detection). The simulator works on numbers you enter.
It does not inspect or control any real operating-system process.

## 1. Overview

### Problem statement

In a multiprogramming system, processes compete for a limited set of resources. A process may
hold some resources while waiting for more. If a group of processes each wait for resources
held by others in the group, none of them can ever proceed: that is a **deadlock**. The
operating system needs a way to look at the current allocation and outstanding requests and
tell which processes are stuck.

### Objectives

- Let a user enter their own system: 1 to 10 processes and 1 to 10 resource types, each type
  with any number of identical instances.
- Run the standard multiple-instance deadlock *detection* algorithm on the backend.
- Show the completion order, the unfinished (deadlocked) processes, and the full trace of the
  algorithm's work, with a plain-language explanation of why each stuck process is stuck.
- Make the algorithm easy to follow and explain in a project review.

### Detection, not avoidance

This project implements deadlock **detection**. It is **not** the Banker's algorithm, which is
deadlock *avoidance*. Detection looks at the resources processes hold now and the requests they
have already made, and reports which processes cannot finish. The Banker's algorithm uses each
process's declared *maximum* demand (the `Max`/`Need` matrices) to decide whether granting a
new request would keep the system in a safe state. There is no `Max` or `Need` anywhere in this
code. A side-by-side comparison is in [docs/algorithm.md](docs/algorithm.md#2-detection-is-not-avoidance-not-the-bankers-algorithm).

## 2. Features

- Process and resource-type counts from 1 to 10, with editable **Available**, **Allocation** and
  **Request** grids labelled `P1, P2, ...` and `R1, R2, ...`.
- Resizing keeps the numbers already typed and fills new cells with `0`.
- Six example scenarios you can load and then edit (see [section 8](#8-using-the-web-interface)).
- A **Detect deadlock** button that calls the real backend (`POST /api/detect`), with a visible
  loading state and protection against double submission.
- A result panel that clearly separates *Deadlock detected* from *No deadlock detected*, with
  per-process outcome chips, the completion order, `Work` at the start and end, and the reason
  the algorithm stopped.
- For deadlocks: a card per stuck process showing the resources it is short of, how many it
  needs, how many are available, and by how much it falls short.
- A collapsible, step-by-step **detection trace** generated by the backend, not by the browser.
- When you click **Detect deadlock**, blank, negative, fractional and non-numeric cells are
  highlighted with a message and nothing is sent. The server validates everything again and has
  the final say.
- Clear messages for network failures, server errors and unexpected responses.
- A result is marked as out of date when you change the inputs after running detection.
- **Clear results** and **Reset to starting example** controls.
- Responsive layout (tables scroll inside their own boxes on narrow screens), visible keyboard
  focus, a skip link, labelled inputs, and status text in addition to colour.
- No internet connection needed once dependencies are installed: no CDN, web fonts or external
  requests. The page uses system fonts and follows the system light/dark setting.

## 8. Using the web interface

1. **Choose the size.** Set *Processes* and *Resource types* (1 to 10 each). The grids resize;
   numbers you already entered are kept and new cells start at `0`.
2. **Enter the data**, or load an example first.
   - **Available:** free instances of each resource type right now.
   - **Allocation:** how many instances of each resource each process holds now.
   - **Request:** how many *more* instances each process is waiting for before it can finish.
   Click a cell and type; the old value is selected so typing replaces it.
3. **Click *Detect deadlock*.** The button shows *Running detection* while waiting and cannot be
   triggered twice. The result appears below and the page scrolls to it.
4. **Read the result** ([section 13](#13-reading-the-result)).
5. **Change anything and run again.** After you edit a value or change the size, the existing
   result is dimmed and marked *You changed the inputs after this result was produced*. It
   describes the earlier numbers until you run detection again.

Other controls:

| Control | What it does |
|---|---|
| *Example* dropdown and **Load example** | Fills the whole form from a scenario and shows what it demonstrates. You can edit it before running. |
| **Reset to starting example** | Restores the starting example ("Two processes deadlocked, one independent") and clears results and messages. |
| **Clear results** | Hides the result. Your inputs are left as they are. Disabled while there is no result. |

The six examples (inputs only; the answers always come from the server):

| Example | Size | Demonstrates |
|---|---|---|
| Two processes deadlocked, one independent | 3 x 3 | A deadlocked pair plus a process that finishes alone |
| Every process can finish | 2 x 2 | The simplest no-deadlock case |
| One process finishing frees another | 2 x 2 | A release that makes a later process runnable |
| Five processes, three resource types | 5 x 3 | A textbook-style system with several instances; no deadlock |
| Five processes, four of them stuck | 5 x 3 | The same system with one extra request that causes a deadlock |
| A process that holds nothing | 3 x 2 | A process that holds nothing counts as finished from the start |

## 9. Input format and validation rules

The server accepts a JSON object with exactly these five fields (other fields are ignored and
not used):

| Field | Meaning | Shape |
|---|---|---|
| `process_count` | `n`, number of processes | integer, 1 to 10 |
| `resource_count` | `m`, number of resource types | integer, 1 to 10 |
| `allocation` | `Allocation[i][j]` | list of `n` rows, each a list of `m` integers |
| `request` | `Request[i][j]` | list of `n` rows, each a list of `m` integers |
| `available` | `Available[j]` | list of `m` integers |

Example:

```json
{
  "process_count": 2,
  "resource_count": 2,
  "allocation": [[1, 0], [0, 1]],
  "request":    [[0, 1], [1, 0]],
  "available":  [0, 0]
}
```

### Rules enforced by the server (`validation.py`)

- The body must be a JSON object (not an array, string, number or `null`).
- All five fields must be present.
- Counts must be real integers from 1 to 10.
- Every entry of `available`, `allocation` and `request` must be a real integer that is 0 or
  more. There is **no upper limit** on how many instances a resource can have; only the number
  of processes and resource types is capped at 10.
- Dimensions must match the counts exactly: `allocation` and `request` need `process_count`
  rows of `resource_count` columns, and `available` needs `resource_count` entries.
- **Nothing is converted.** The string `"2"`, the decimal `2.0` and the boolean `true` are all
  rejected where an integer is required, as are `null`, negative numbers and nested lists or
  objects in place of numbers.
- Matrices and vectors must be lists (JSON arrays).
- Validation reports the first problem it finds, with the location, for example
  `allocation row 2, column 1 (P2, R1) must be a non-negative integer (0, 1, 2, ...), got -1.`

### Rules enforced by the page before sending

Each cell must be digits only: no sign, decimal point or comma, spaces, exponent notation, or
blank. A value such as `007` is accepted and read as 7. The page also rejects values above
9007199254740991 (the largest integer JavaScript represents exactly), which is stricter than
the server. The page only gives quick feedback; the server's validation is authoritative.

## 10. The API

The page uses this endpoint, and you can call it directly.

### Routes

| Method and path | Purpose |
|---|---|
| `GET /` | The simulator page |
| `GET /static/...` | Its CSS and JavaScript |
| `GET /health` | `{"status": "ok"}` |
| `POST /api/detect` | Run detection |

### Calling it

```bash
curl -s -X POST http://127.0.0.1:5001/api/detect \
  -H "Content-Type: application/json" \
  -d '{"process_count":2,"resource_count":2,"allocation":[[1,0],[0,1]],"request":[[0,1],[1,0]],"available":[0,0]}'
```

### Successful response (HTTP 200)

The body is exactly the result of `detect_deadlock`. A detected deadlock is still HTTP 200,
because it is a valid answer.

| Field | Meaning |
|---|---|
| `success` | `true` |
| `status` | `"NO_DEADLOCK"` or `"DEADLOCK_DETECTED"` |
| `message` | One-sentence summary |
| `process_count`, `resource_count` | Echo of the size |
| `deadlocked_processes` | Labels still unfinished, e.g. `["P2","P3"]` |
| `finished_processes` | Processes that finished (started finished, or completed during detection), in index order |
| `completion_sequence` | Processes in the order the algorithm completed them (does **not** include those that started finished) |
| `initially_finished` | Processes that held nothing at the start |
| `finish_status` | `{"P1": true, ...}`: the final `Finish` array |
| `initial_work`, `final_work` | `Work` at the start and when the algorithm stopped |
| `trace` | List of scans (below) |
| `stop_reason` | Why the algorithm stopped |
| `blocked_explanations` | For each deadlocked process: `request`, `allocation`, `final_work`, `shortages` (`resource`, `requested`, `available`, `shortfall`) and a sentence in `explanation`; `{}` when there is no deadlock |

Each `trace` entry describes one scan: `iteration`, `work_before`, `finish_before`,
`considered` (every unfinished process with its `request` and `can_satisfy`), `selected`,
`selected_request`, `allocation_released` and `work_after`. When the algorithm stops with
unfinished processes, the last entry has `selected: null` (the scan in which nobody fit);
when every process finishes there is no such entry.

### Errors

Every error is JSON in the same shape:

```json
{ "success": false, "error": "<code>", "message": "<text>" }
```

`validation_error` also carries a `field` (the field at fault, or `null`).

| Situation | HTTP | `error` | Example message |
|---|---|---|---|
| Valid JSON but bad data | 400 | `validation_error` | `available entry 2 (R2) must be a non-negative integer (0, 1, 2, ...), got -1.` |
| Body is valid JSON but not an object | 400 | `validation_error` | `Request body must be a JSON object, got null.` |
| Body is not valid JSON | 400 | `invalid_json` | `Request body is not valid JSON (Expecting value at line 1, column 6).` |
| Empty or whitespace-only body | 400 | `missing_body` | `Request body is empty. Send a JSON object.` |
| Body present but `Content-Type` is not JSON | 415 | `unsupported_media_type` | `Content-Type must be application/json.` |
| Body larger than 100 KB | 413 | `payload_too_large` | `Request body is too large (limit 100 KB).` |
| Unknown URL | 404 | `not_found` | `The requested URL was not found.` |
| Wrong method (for example `GET /api/detect`) | 405 | `method_not_allowed` | `This URL does not support that HTTP method.` (with an `Allow` header) |
| Unexpected server error | 500 | `internal_error` | `Internal server error. Please try again.` |

Unexpected errors are logged on the server (with the traceback) and answered with a generic
message; no stack trace or internal detail is sent to the client. The algorithm is never run
on input that failed validation.

## 11. The algorithm

Notation: `n` processes, `m` resource types, `Available`, `Allocation` and `Request` as above.

```text
Work   = copy of Available
Finish[i] = true  if Allocation[i] is all zeros      (holds nothing)
          = false otherwise

repeat:
    find the lowest-numbered i with Finish[i] = false
        and Request[i][j] <= Work[j] for every resource type j
    if there is no such i: stop
    otherwise:
        Work      = Work + Allocation[i]    # Pi finishes and releases what it holds
        Finish[i] = true

every i with Finish[i] = false is reported as deadlocked
```

Key points:

- **Element-wise comparison.** A request fits only if *every* resource type fits; having enough
  of one type does not help.
- **Release on completion.** A process's allocation goes back into `Work` only after the
  process has been selected as able to finish.
- **Zero-allocation processes start finished.** A process that holds nothing cannot be
  blocking anyone. As a consequence it is never reported as deadlocked, even if its own request
  can never be met.
- **Lowest-index-first** makes the trace repeatable. It affects only the order shown, not
  which processes are reported as deadlocked, because finishing a process only ever adds to `Work`.
- **Complexity.** Time O(m · n²). The algorithm's working data is O(n · m); the returned trace
  can be O(n² · m) in the worst case.
- The caller's input lists are copied and never modified.

The complete explanation, pseudocode, comparison with the Banker's algorithm, and a second
worked example are in [docs/algorithm.md](docs/algorithm.md).

## 12. Worked example

The starting example ("Two processes deadlocked, one independent") is a good first run. Here we
use a smaller mixed case (three processes, two resource types) that you can type in with
*Processes* = 3 and *Resource types* = 2:

```text
Available = [0, 1]

        Allocation    Request
        R1 R2         R1 R2
  P1     1  0          0  1
  P2     0  1          2  0
  P3     1  0          0  2
```

Everyone holds something, so nobody starts finished. `Work = [0, 1]`.

| Scan | `Work` before | Does each unfinished request fit? | Selected | `Work` after |
|---|---|---|---|---|
| 1 | `[0, 1]` | P1 `[0,1]`: yes. P2 `[2,0]`: no (needs 2 of R1, 0 free). P3 `[0,2]`: no (needs 2 of R2, 1 free). | P1 | `[0,1] + [1,0] = [1,1]` |
| 2 | `[1, 1]` | P2 `[2,0]`: no (2 > 1). P3 `[0,2]`: no (2 > 1). | none: stop | `[1, 1]` |

What the application reports (this is the real output of the code for this input):

- **Status:** *Deadlock detected*: `P2, P3 cannot finish`.
- **Completion order:** `P1`. **Deadlocked:** `P2, P3`. **Finished from the start:** none.
- **Work at the start:** `[0, 1]`. **Work at the end:** `[1, 1]`.
- **Why it stopped:** `No unfinished process has a request that fits within Work [1, 1]. Stopped with P2, P3 unfinished.`
- **Blocked-process explanations:**
  - `P2 cannot finish: it is waiting for R1 (needs 2, only 1 available) in the final Work vector.`
  - `P3 cannot finish: it is waiting for R2 (needs 2, only 1 available) in the final Work vector.`

Interpretation: `P1` can finish, and its release raises `R1` to 1. That is still not enough.
`P2` needs two `R1` and `P3` needs two `R2`, and the only way to get more would be for `P2` or
`P3` to finish and release what it holds, which they cannot do while waiting. They are stuck on
each other, and the unfinished processes are reported as deadlocked.

## 13. Reading the result

**Banner.** *No deadlock detected* means there is an order in which every process can finish,
using the resources released along the way. *Deadlock detected* means the listed processes
cannot finish with the numbers given.

**Process chips.** One per process:

| Chip text | Meaning |
|---|---|
| `Pi finishes at step k` | `Pi` was the k-th process the algorithm completed |
| `Pi holds nothing: finished from the start` | `Pi` started with `Finish = true` because it holds no resources |
| `Pi deadlocked: cannot finish` | `Pi` was still unfinished when the algorithm stopped |

**Completion order.** The order in which the algorithm completed processes, lowest number
first. It is *one* valid order, not the only one, and it is not a guarantee about every
possible schedule. Processes that started finished are not in it; they are listed under
*Finished from the start*.

**Work at the start and end.** `Work` is the algorithm's running count of free instances. It
starts equal to Available and grows as processes finish and release. *Work at the end* is what
was free when the algorithm stopped. It is the vector the stuck processes are compared against.

**Why it stopped.** Either all processes finished, or no unfinished process had a request that
fits within `Work`.

**Why these processes are stuck.** One card per deadlocked process. The table lists each
resource it is short of: *Needs* (its request), *Available* (in the final `Work`) and *Short by*.
Below it, *Holds now* is its allocation and *Still requests* its outstanding request.
Only resources it is actually short of appear in the table.

**Detection trace.** One card per scan, in order:
- *Process states before this scan* (finished / not finished),
- *Work before this scan*,
- a table of every unfinished process checked, lowest number first, with its request and
  whether it fits in `Work`. The one that is selected is marked,
- for a successful scan, what the selected process releases and *Work after this scan*,
- for the final scan of a deadlock, a *Stop* note: nobody fit.

A process that shows *No* in an early scan is not necessarily deadlocked. It may fit later,
after other processes release resources. Only processes still unfinished when the algorithm
stops are reported as deadlocked.

## 14. Scope, assumptions and limitations

**Scope.** A single snapshot: the Allocation, Request and Available numbers you enter. The
output is that snapshot's classification, trace and explanations.

**Assumptions of the standard model.**
- A process can finish when its **whole** outstanding request can be satisfied at once.
- A finished process releases **everything** it holds.
- A process that holds nothing is treated as finished from the start.
- The numbers entered are correct and consistent. The result is only as good as the input.

**Limitations.**
- Nothing inspects real operating-system processes or resources.
- Only detection is implemented. There is no Banker's algorithm, no deadlock recovery
  (such as terminating a process or preempting resources), and no prevention.
- `Available` is entered directly. The simulator does not check it against a total-resource
  vector; the optional Total extension (`Total = Available + sum of Allocation`) is not
  implemented, so it cannot catch an impossible combination of numbers.
- There is no process/resource graph drawing. Results are shown as chips, tables and the trace.
- The completion order is one valid order, not a statement about every possible schedule.
- Limits: 1 to 10 processes and 1 to 10 resource types; request bodies up to 100 KB; the page
  waits at most 15 seconds for the server; the page accepts cell values up to
  9007199254740991.
- Nothing is saved. Reloading the page returns to the starting example.
- It runs on Flask's development server in debug mode for local use. It is not hardened for
  production and has no authentication.

## 15. Troubleshooting

| Problem | Likely cause and fix |
|---|---|
| `python: command not found` | The virtual environment is not active, or use `python3`. Run `source venv/bin/activate` from the project folder. |
| `ModuleNotFoundError: No module named 'flask'` | Dependencies not installed in the active environment. Activate `venv` and run `pip install -r requirements.txt`. |
| `ModuleNotFoundError: No module named 'deadlock'` (or `validation`, `app`) when testing | Run pytest from the project folder, which contains `pytest.ini`: `python -m pytest -v`. |
| `Address already in use` | Another program uses port 5001. Find it with `lsof -i :5001`, stop it, or change `port=5001` at the bottom of `app.py` and use the new port in the URLs. |
| Page is blank or unstyled | The browser may have cached old files. Hard refresh (Cmd+Shift+R). Also check the terminal for errors, and that you opened `http://127.0.0.1:5001/` and not a file on disk. |
| "Could not reach the server" in the page | The Flask server stopped or is on another port. Restart it with `python app.py`. |
| An input is highlighted red and nothing happens on **Detect deadlock** | A cell is blank, negative, has a decimal point, or contains text. Read the red message above the button and fix the listed cells. |
| A message beginning "The server rejected the input" | The server's validation caught something the page did not. The message says which field and what is wrong. |
| `test_javascript_logic_tests_pass_under_node` is **skipped** | Node.js 18 or newer is not installed. Install it to run the JavaScript tests, or ignore the skip. |
| Tests fail after editing `static/js/samples.js` | The examples must stay valid JSON and each has an expected answer in `tests/test_frontend.py`. Update both together. |
